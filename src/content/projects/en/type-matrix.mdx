## What it is

A game room built on creature data, and not an encyclopedia: nobody comes to
look up an entry, they come to play or to calculate. Five modes:

- **Battle calculator.** Attacker, defender, move, level, IVs, EVs and nature
  in; the sixteen-roll damage range and the share of the defender's HP out.
- **Team builder.** Up to six species, with their shared weaknesses, STAB
  coverage and the gaps against real dual-type defenders.
- **Hangman.** A species name, letter by letter, six misses allowed.
- **Stats & types.** Guess a species from feedback on its types and an arrow
  per base stat, in eight guesses.
- **Daily puzzle.** One round of each game a day, the same for everyone, each
  with its own streak and leaderboard.

There is no silhouette mode, on purpose: it would need official art, and the
project uses none. Stats & types took its place — you guess from the numbers,
not the shape.

## Ground rules

- **Free plans, every one of them.** Vercel Hobby for the app and Neon for the
  database, which means no cron worth the name and a Postgres that sleeps.
- **A public repository.** Anything that decides tomorrow's puzzle has to be
  something the code alone cannot reproduce.
- **No login.** A player should be able to play the moment the page loads, and
  still keep a streak.
- **No official art.** No sprites, no logos and no franchise name as the
  product's brand.

## What it sets out to prove

Two claims. The interface is the vehicle for both.

### The client never knows the answer

Guessing games over a public dataset usually send the answer to the browser and
let the interface hide it, so anyone who opens the developer tools has finished
the game — and a daily leaderboard on top of that measures nothing.

Here a game is a database row. The browser holds only its id, and every guess
is a `POST` the server validates and answers with feedback. The answer leaves
the server once, in the response that ends the game.

The trap specific to Next.js is that any prop a Server Component hands a Client
Component is serialised into the page's payload — so a hidden answer passed as
a prop is not hidden at all. Here the answer is never a prop, and the module
that loads the species data is marked `server-only`, so a client import of it
breaks the build rather than leaking.

The proof is a test that plays full games through the API, in every mode, the
daily puzzle and giving up included, and checks that no response before the
last one contains the answer — not its id, not its name, not its stat line. It
was checked against a deliberate leak: with the answer left in the view, its
cases fail.

### The formulas are exact

/>

The damage formula is a chain of multipliers, and the games round at every
step of it. A calculator that rounds once at the end, or uses a plain
`Math.round`, shows a number that looks complete and is off by a point or two —
exactly the margin a player is using it to decide.

Stats, damage and the type chart here follow the games' rounding at each step.
The test vectors came from a reference calculator, `@smogon/calc`, run outside
the repository as an oracle — never a dependency — and copied in by hand, so
they were not generated by the code they test.

The lesson worth keeping: the oracle, not the written spec, settled which step
uses `floor` and which uses the games' half-down rounding. The bug those
vectors exist to catch is a plain `Math.round`.

What the calculator does not model — abilities, held items, weather, terrain,
Terastallization, doubles — it says so above the form, instead of showing a
number that looks complete.

## The daily puzzle

<img
  src="/case-studies/type-matrix/hangman.webp"
  width="1280"
  height="800"
  loading="lazy"
  alt="A Hangman game in progress: part of a two-word name revealed, the gallows with a head and body drawn for two misses, the message that N is in the name with four misses left, and the letter keyboard with the letters already played dimmed."
/>

- **Deterministic, and still unguessable.** Each day's answer is the pool
  shuffled once by an HMAC of a server-side secret, then indexed by the puzzle
  number. Nothing is scheduled and nothing is stored in advance: the puzzle is
  computed, not published. A seed taken from the date alone would let anyone
  with the public repo compute tomorrow's answer; the secret is what stops it.
  Shuffling once means no repeats until the pool cycles, and Hangman draws from
  a separate order, so the two rounds never share a day's species.
- **Timezones without trusting the client.** The browser sends its local date,
  and the server accepts it only if that date is "today" somewhere on Earth,
  from UTC−12 to UTC+14. A puzzle closes when its date is no longer today
  anywhere, and an unfinished game then counts as lost — so an answer seen
  elsewhere cannot win it late.
- **Streaks are derived, never stored.** They count consecutive puzzle numbers,
  not calendar days, and come from the results themselves rather than a counter
  that can drift.
- **A leaderboard measured by the database.** Fewest guesses or misses first,
  then the time from the game's creation to the winning guess — both on the
  database clock. The client's clock is never asked.

## Stack

- **Next.js with a server**, unlike the portfolio's static export: every guess
  is a request, and the answer lives behind it.
- **Plain SQL on Neon Postgres, no ORM.** Two guesses sent at once cannot both
  count, and a give-up cannot land alongside a guess; optimistic checks in the
  queries handle it, and a unique key makes the database enforce one daily game
  per player and puzzle. No library was added for state, HTTP or data access.
- **Identity without a login.** A signed `httpOnly` cookie is issued on the
  first save, not the first visit, so bots and people who only look leave no
  rows. The JSON-only routes stop a cross-site form from swapping the cookie,
  and the routes that create rows are throttled per IP and hour, counted in
  Postgres: 10 nicknames and 60 new games.
- **A data snapshot in the repository.** The species data is never fetched at
  runtime. A manual ingest from PokéAPI writes one JSON file that is committed,
  so a re-ingest arrives as a diff someone can review.
- **Boundaries a linter enforces — and a test that checks the linter.** One
  module per domain, a public `index.ts` each, one-way dependencies checked by
  `eslint-plugin-boundaries`. The rules once passed while checking nothing,
  when an install script was blocked and an import stopped resolving, so a test
  now proves they catch a real violation.
