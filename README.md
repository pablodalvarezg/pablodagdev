# pablodagdev

Portfolio of Pablo Álvarez Graña, full-stack and low/no-code developer in Buenos
Aires. A Next.js site in English and Spanish, built as a static export: every
page is plain HTML with the content already in it, and each side project gets a
page that doubles as its case study, styled by its own theme.

Working agreements live in [CLAUDE.md](CLAUDE.md); scope and phases in
[PORTFOLIO_BRIEF.md](PORTFOLIO_BRIEF.md). [AGENTS.md](AGENTS.md) is written by
`next dev` and points at the docs bundled with the installed Next version.

## Requirements

- **Node 24.21.0**, the active LTS. `nvm use 24.21.0` if you keep several.
- **npm**. The lockfile is `package-lock.json`.

## Running it

```bash
npm install     # first time, and whenever dependencies change
npm run dev     # http://localhost:3000
```

| Command | What it does |
| --- | --- |
| `npm run dev` | Local server on :3000, with hot reload |
| `npm run build` | Static export into `out/` |
| `npm run preview` | Serves `out/` the way a host will |
| `npm run check` | `next typegen` then `tsc --noEmit` |
| `npm run lint` | ESLint, including the module boundary rules |
| `npm run format` | Prettier |
| `npm test` | Vitest |

Before calling anything done: `npm run check && npm run lint && npm test`.

`check` runs `next typegen` first on purpose. `PageProps` and `LayoutProps` are
generated by Next, so `tsc` alone fails on a clean checkout.

Canonical URLs and hreflang come from `SITE_URL`, which falls back to the dev
server. Production sets it to the real domain.

## Layout

```
src/
├─ app/                    Routing and composition only.
│  └─ [lang]/              The locale is the first segment, so this layout
│     ├─ layout.tsx        is the root layout and owns <html lang>.
│     └─ page.tsx          The hub.
├─ modules/                One per domain, each with a public API in index.ts.
│  ├─ experience/          domain · data · ui — the work timeline
│  ├─ hub/                 The neutral sections: hero, what I do, about, contact
│  ├─ i18n/                Locales, dictionaries, localized paths
│  └─ theming/             Theme registry and the light/dark toggle
├─ shared/                 ui primitives and config. Never imports a module.
└─ app/globals.css         Tailwind entry and the semantic token contract
```

Dependencies point one way — `app → modules → shared` — and a module is reached
through its `index.ts`. ESLint enforces it, so a deep import fails
`npm run lint` rather than review.

## Server and client components

Everything is a Server Component unless a file opens with `"use client"`. On a
static export that means it runs at build time and ships no JavaScript, which is
why the content is in the HTML.

Two components cross into the browser, and both earn it:

- **`SchemeToggle`** needs a click handler and `localStorage`.
- **`LanguageSwitcher`** needs `usePathname()`. A Server Component does not know
  the path, and when this took it as a prop, a page that forgot to pass it
  linked to the locale home instead of its own translation, with no error and no
  failing build.

`"use client"` is contagious downward: everything the file imports becomes
client too. Keep it as low in the tree as possible, and when a client component
has to wrap static content, pass that content as `children` so it keeps
rendering on the server.

Watch the bundle size `next build` prints. If it grows, someone added a
`"use client"` that did not need to be there.

## Adding a case study

> **Not wired yet.** The content collection, the schema and the project route are
> still to be built. This is the procedure they are being built to support.

A case study is the page of a side project. There is no separate collection.

1. Write `src/content/projects/en/<slug>.mdx` and its Spanish twin in
   `src/content/projects/es/<slug>.mdx`. Both need the same slug; that is what
   pairs them for hreflang.
2. Fill the frontmatter. The Zod schema is the contract, and the build fails on
   anything missing or unknown, including a `theme` that is not registered.
3. Follow the body structure: problem, constraints, solution, stack, result,
   what you would improve.
4. Leave `draft: true` until it is finished. Drafts render while developing and
   are absent from a production build, so nothing half-written ships.

Never invent a number. An empty result section beats an estimated one.

## Creating a theme

> **One theme exists so far**, the neutral `base` used by the hub. A world gets
> its token file when its project does.

A theme is a world: its own palette, type and radii, applied by changing one
frontmatter field.

1. Add `src/modules/theming/themes/<name>.css` with a `[data-theme='<name>']`
   block that redefines the semantic tokens.
2. Import it from `src/app/globals.css`, next to the other worlds. Tailwind
   needs a single CSS entry, which is why the import points into the module.
3. Register the name in `THEME_NAMES` in
   `src/modules/theming/domain/theme-registry.ts`. That array is the single
   source of valid names and the content schema reads it, so an unregistered
   theme fails the build instead of rendering unstyled.
4. Check contrast in both schemes before committing. Every token pair that
   carries text must reach AA.

One rule that is easy to get wrong: text sitting on a fill of `--color-accent`
takes `--color-accent-fg`, never `--color-fg`. In dark both `fg` and the lime
accent are light, and the pair reads at 1.3:1.

Components read semantic tokens and never a raw color, font or radius, so
adding a world touches no component.
